# 面试题：侧边栏折叠功能

> 基于"心理健康AI助手"管理后台项目的真实实现，可作为 Vue 组件通信的实战案例

---

## 面试题（基于本项目实现）

##### 1. 在你的项目中，父组件和子组件之间是怎么通信的？

回答：以我做的侧边栏折叠功能为例。`collapsed` 状态放在布局组件 BackendLayout 中，通过 `:collapsed` prop 向下传给 SideBar 和 NavBar 两个子组件；NavBar 里点击折叠按钮时，通过 `emit('toggle')` 向上通知父组件修改状态。

```html
<!-- BackendLayout.vue -->
<SideBar :collapsed="collapsed" />
<NavBar :collapsed="collapsed" @toggle="collapsed = !collapsed" />
```

这就是标准的 props down / events up 单向数据流。

##### 2. 多个组件共享同一个状态时，你是怎么组织的？

回答：用**状态提升**。collapsed 被 NavBar（触发折叠）和 SideBar（响应折叠）两个兄弟组件都需要，放在任何一方，另一方都要跨组件取状态。所以我把状态提升到它们的共同父组件 BackendLayout 统一持有，两个子组件只通过 props 读、emit 写。

判断标准：同页面的 UI 状态用状态提升；跨页面持久化或领域数据（用户信息、文章列表）用 Pinia。

##### 3. Vue 的 props down / events up 是什么意思？

回答：指 Vue 单向数据流——数据只能从父组件经 props 流向子组件，子组件不能直接修改 prop，修改意图要通过 emit 事件通知父组件，由父组件改状态后再流回来。

在我的折叠功能里：NavBar 不直接改 collapsed，而是 `emit('toggle')`，由 BackendLayout 执行 `collapsed = !collapsed`，新值再经 props 流回两个子组件。这保证了数据变化永远可追踪。

##### 4. ref 是怎么工作的？为什么改 ref 会触发子组件更新？

回答：ref 是 Vue 3 的响应式基本单元，内部通过 Proxy 拦截读写。当 BackendLayout 中 `collapsed.value` 被重新赋值时，Vue 检测到变化，重新执行组件渲染，新的 prop 值流向 SideBar 和 NavBar，触发它们的模板更新。

```ts
const collapsed = ref(false);
// collapsed = !collapsed 后，所有依赖它的视图自动更新
```

整个折叠过程中没有一行手动 DOM 操作，这就是声明式渲染。

##### 5. el-menu 的 collapse 属性是干嘛的？

回答：Element Plus 菜单的内置折叠能力。设为 true 时菜单自动收窄为只显示图标，还内置了折叠动画、图标居中、悬停 tooltip，不用手写。

```html
<!-- SideBar.vue -->
<el-menu :collapse="collapsed" :collapse-transition="true"></el-menu>
```

我只需把 collapsed prop 绑上去，配合 `el-aside :width="collapsed ? '64px' : '264px'"` 就完成了整个折叠效果。

##### 6. 为什么不把 collapsed 放在 SideBar 里，让 NavBar 直接调用？

回答：技术上可行（defineExpose + ref 调用、事件总线 mitt），但都有问题：ref 调用要求 NavBar 了解 SideBar 的内部实现，耦合高；mitt 是盲通信，DevTools 里看不到数据流向。

本质原因是 collapsed 是**布局级状态**，不属于任何一方。放在兄弟组件里会造成职责错位，也破坏单一数据源（SSOT）——状态应该只有一个权威所有者，其他组件读它用 props、改它用 emit。

##### 7. 如果面包屑组件也要用折叠状态怎么办？什么时候用 Pinia？

回答：面包屑和 SideBar/NavBar 还在同一棵布局子树下，共同祖先仍是 BackendLayout，继续用状态提升即可，不需要新方案。

引入 Pinia 的时机：状态需要跨页面持久化（登录态、主题）、共同祖先太深导致 prop drilling（4-5 层以上）、或状态是领域数据（商品、文章）而非 UI 状态。折叠状态是纯 UI 状态且范围局限，用 Pinia 反而过度设计。

##### 8. v-if 和 v-show 有什么区别？折叠功能里怎么选的？

回答：v-if 条件为 false 时销毁 DOM，为 true 时重新创建；v-show 只是切换 display: none，DOM 始终存在。

我的选择：折叠按钮图标用 `v-if="!collapsed"` / `v-else` 切换 Fold/Expand，因为两个图标不会同时存在；brand 区文字隐藏用 `v-show`，避免频繁创建销毁 DOM。

## 项目背景

**场景**：后台管理系统的侧边栏折叠——点击顶部导航栏的折叠按钮，左侧菜单栏从 264px 收缩到 64px，只显示图标。

**组件结构**：

```
BackendLayout.vue    ← 页面骨架（状态持有者）
├── SideBar.vue      ← 侧边栏（响应者）
└── NavBar.vue       ← 顶部导航栏（触发者）
```

---

## 核心实现

### 1. 状态提升到父组件

**为什么？** `collapsed` 被 NavBar 和 SideBar 两个兄弟组件都需要访问。如果放在任一个子组件里，另一个子组件就拿不到。所以**提升到共同的父组件 BackendLayout**。

```ts
// BackendLayout.vue
const collapsed = ref(false);
```

### 2. Props 向下传递（父 → 子）

```html
<!-- BackendLayout.vue 模板 -->
<SideBar :collapsed="collapsed" />
<NavBar :collapsed="collapsed" />
```

子组件声明接收：

```ts
// SideBar.vue
defineProps<{ collapsed: boolean }>();

// NavBar.vue
defineProps<{ collapsed: boolean }>();
```

### 3. Emit 向上通知（子 → 父）

NavBar 里的折叠按钮被点击时，不能直接改 prop（Vue 单向数据流），而是 emit 一个事件让父组件改：

```ts
// NavBar.vue
const emit = defineEmits<{ toggle: [] }>();
```

```html
<!-- NavBar.vue 模板 -->
<el-icon @click="emit('toggle')">
  <Fold v-if="!collapsed" />
  <Expand v-else />
</el-icon>
```

父组件接收事件并翻转状态：

```html
<!-- BackendLayout.vue -->
<NavBar @toggle="collapsed = !collapsed" />
```

### 4. SideBar 响应状态变化

不用写手动 DOM 操作，直接用 Element Plus 内置能力：

```html
<!-- SideBar.vue -->
<el-aside :width="collapsed ? '64px' : '264px'">
  <el-menu :collapse="collapsed" :collapse-transition="true">
  <!-- Element Plus 的 el-menu 内置了折叠动画、图标居中、tooltip -->
</el-aside>
```

## 完整数据流

```
NavBar 按钮点击
    ↓ emit('toggle')
BackendLayout collapsed 翻转（ref 响应式触发）
    ↓ :collapsed prop 重新绑定
SideBar el-menu :collapse 变化 → 自动折叠
SideBar el-aside :width 变化  → 宽度收缩
NavBar Fold/Expand 图标        → 条件渲染切换
```

## 可迁移的知识点

| 知识点                    | 项目中如何应用                              |
| ------------------------- | ------------------------------------------- |
| **单向数据流**            | props 只读，emit 通知父组件修改             |
| **状态提升**              | 多个组件共享状态时，提升到最近的共同祖先    |
| **Vue 响应式**            | ref 值变化自动触发模板更新                  |
| **Element Plus 内置能力** | `el-menu :collapse` 避免手动写折叠逻辑      |
| **条件渲染**              | `v-if`/`v-else` 切换图标，`v-show` 控制显隐 |

## 深入理解：为什么状态必须提升到共同祖先？

### 问：兄弟组件间不能通信吗？为什么不能把 collapsed 放在任意一个兄弟里？

兄弟组件**技术上可以通信**（ref 跨组件调用、事件总线 mitt），但都有问题：

| 方案                             | 问题                                            |
| -------------------------------- | ----------------------------------------------- |
| `defineExpose` + 父组件 ref 中转 | NavBar 必须知道 SideBar 暴露了什么，耦合度高    |
| 事件总线 mitt                    | 盲通信，DevTools 里看不到谁发谁收，数据流不透明 |

**本质原因**：`collapsed` 是**布局级状态**，不属于 SideBar 也不属于 NavBar。放在任一方都是"让不该管的组件当了状态管理员"。

### 问：状态提升到哪一层为止？Pinia 什么时候上？

**状态提升原则**：放到所有需要它的组件的**最低共同祖先**，不要无意义地往上提。

| 判断条件                                                         | 方案                    |
| ---------------------------------------------------------------- | ----------------------- |
| 几个组件在**同一个页面**共享 UI 状态（collapsed、弹窗开关、tab） | 状态提升 + prop/emit    |
| 状态要**跨页面持久化**（登录态、主题）                           | Pinia                   |
| 共同祖先太高（4-5 层以上），prop drilling 严重                   | Pinia 或 provide/inject |
| 状态是**领域数据**（商品列表、文章、用户），不是 UI 状态         | Pinia                   |

### 补充：还有一种兄弟通信方式——Provide/Inject

```ts
// BackendLayout.vue
provide("sidebar-collapsed", collapsed);

// 任意后代组件
const collapsed = inject<Ref<boolean>>("sidebar-collapsed")!;
```

适用于层级深、不想逐层传 props 的场景。但折叠按钮层级浅，prop/emit 更清晰可读。

### 核心原则：单一数据源（SSOT）

> 任何数据在应用中只有一个权威所有者。

所有组件从同一个地方读状态，所有修改请求都发给所有者。这样永远不会出现"A 组件说折叠了，B 组件说还没折叠"的不一致。
